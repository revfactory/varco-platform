# 게임 시스템 명세와 밸런스 테이블

시스템 명세는 엔지니어가 그대로 구현하고, QA 가 그대로 대조하고, 밸런스 분석가가 그대로 시뮬레이션할 수 있어야 한다. 세 사람이 같은 문장을 다르게 읽으면 기획, 구현, 검증이 서로 다른 게임을 다루게 된다. 그래서 이 스킬은 문장보다 표와 공식을 앞세운다.

파일 경로와 형식은 산출물 계약서(`.claude/skills/varco-game-studio/references/contracts.md` 3절, 4-1절)를 따른다.

## 1. 작업 순서

1. 컨셉의 코어 루프 단계마다 그 단계를 움직이는 시스템을 찾는다. 예: "코너에서 드리프트로 부스트를 모은다" → 차량 조작 시스템, 부스트 게이지 시스템.
2. 시스템 목록을 만들고 컨셉 범위 밖인 것은 지운다.
3. 시스템마다 2절 템플릿으로 명세를 쓴다.
4. 명세에 나온 숫자를 모두 밸런스 CSV 로 옮기고 `_schema.json` 을 쓴다(3절).
5. 스키마 검사를 돌린다.
   `python3 .claude/skills/balance-simulation/scripts/check_balance_tables.py _workspace/{slug}/01_systems_balance`
6. 통과하면 `balance` 에게 검증을 요청하고, `ux`·`level` 에게 플레이어에게 보여 줄 수치와 메커닉을 알린다.

## 2. 시스템 명세 템플릿 — `_workspace/{slug}/01_systems_spec.md`

```markdown
# {게임 제목} 시스템 명세

## 가정
## 시스템 목록
| 시스템 | 코어 루프 단계 | 밸런스 표 | 우선순위(P0/P1) |

## {시스템 이름}
### 목적
이 시스템이 핵심 재미에 무엇을 보태는지 한두 문장.

### 규칙
1. 플레이어가 ○○하면 ○○된다. (조건과 결과를 한 문장에 하나씩)

### 공식
| 이름 | 공식 | 반올림 | 최소 | 최대 |
| --- | --- | --- | --- | --- |
| 피해량 | `attack × (1 - defense_pct / 100)` | 내림 | 1 | - |

### 상태 전이
| 현재 상태 | 사건 | 조건 | 다음 상태 | 부수 효과 |
| --- | --- | --- | --- | --- |
| idle | 입력: 드리프트 키 | speed ≥ `vehicles.csv:drift_min_speed_px_s` | drifting | 부스트 충전 시작 |

### 플레이어에게 보이는 값
| 값 | 출처(표:열 또는 상태) | 갱신 시점 |

### 예외와 경계
- 값이 0 이 되거나 최대를 넘을 때 어떻게 하는가

## 쟁점
balance·director 와 합의하지 못한 것(양쪽 근거)

## 변경 기록
| 날짜 | 표:열 | 이전 | 이후 | 이유 |
```

### 규칙을 쓰는 요령

- **조건과 결과를 분리한다.** "적을 처치하면 경험치를 얻고 레벨업할 수도 있다"는 두 규칙이다. 한 문장에 규칙 하나를 쓴다. QA 가 규칙마다 테스트 케이스를 하나씩 만든다.
- **공식은 CSV 열 이름으로 쓴다.** 숫자 대신 `enemies.csv:hp` 처럼 표와 열을 적는다. 숫자를 본문에 쓰면 표를 고칠 때 본문이 낡는다.
- **반올림과 한계를 밝힌다.** 소수점이 나오는 공식은 내림·반올림·올림을, 음수가 될 수 있는 값은 최솟값을 적는다. 엔지니어가 임의로 정하면 시뮬레이션과 구현 결과가 달라진다.
- **무작위는 확률과 분포를 적는다.** "가끔 치명타"가 아니라 "`crit_rate_pct` 확률로 피해량 × `crit_mult`, 판정마다 독립"처럼 적는다. 시뮬레이션이 같은 분포를 쓸 수 있어야 한다.
- **상태 전이는 빠짐없이 적는다.** 모든 상태에서 모든 사건이 어디로 가는지 적고, 아무 일도 없으면 "변화 없음"이라고 적는다. 중간 상태에서 최종 상태로 가는 전이가 빠지면 게임이 멈춘다.

## 3. 밸런스 테이블 규칙

### CSV — `_workspace/{slug}/01_systems_balance/{table}.csv`

- 파일 이름은 영문 snake_case 복수형(`enemies.csv`, `vehicles.csv`, `levels.csv`, `economy.csv`)으로 짓는다.
- 첫 열은 `id` 다. 영문 snake_case, 파일 안에서 유일하다. 레벨 문서와 코드가 이 값으로 행을 찾는다.
- 열 이름은 영문 snake_case 이고 단위를 뒤에 붙인다: `_s`(초), `_ms`, `_px`, `_px_s`(초당 픽셀), `_m`, `_pct`(백분율 0~100), `_mult`(배수). 단위가 없으면 정수 개수나 점수다.
- 백분율은 0~100 으로 쓴다. 0~1 과 섞으면 코드가 100배 틀린 값을 쓴다.
- UTF-8(BOM 없음), 쉼표 구분, 한 행 한 개체. 빈칸은 쓰지 않는다. 값이 없으면 스키마에서 그 열을 선택으로 두지 말고 기본값을 채운다.
- 한 게임 전체에 걸친 상수(중력, 한 판 시간 등)는 `globals.csv` 에 `id,value,unit,description` 형태로 둔다.

```csv
id,hp,attack,defense_pct,move_speed_px_s,reward_gold
grunt,90,12,0,120,5
drone,60,8,10,180,7
boss_core,1200,30,25,60,200
```

### 스키마 — `_workspace/{slug}/01_systems_balance/_schema.json`

표마다 설명과 열 정의를 적는다. 열 정의에는 `type`(`string`, `int`, `float`, `bool`)과 필요하면 `min`, `max`, `enum`, `unit`, `description` 을 쓴다. 검사 스크립트와 프로토타입 코드가 이 파일로 값을 검증한다.

```json
{
  "enemies": {
    "description": "적 기본 능력치",
    "columns": {
      "id": {"type": "string"},
      "hp": {"type": "int", "min": 1, "description": "최대 체력"},
      "attack": {"type": "int", "min": 0},
      "defense_pct": {"type": "float", "min": 0, "max": 90, "unit": "%"},
      "move_speed_px_s": {"type": "float", "min": 0},
      "reward_gold": {"type": "int", "min": 0}
    }
  },
  "globals": {
    "description": "게임 전체 상수",
    "columns": {
      "id": {"type": "string"},
      "value": {"type": "float"},
      "unit": {"type": "string"},
      "description": {"type": "string"}
    }
  }
}
```

- 스키마의 표 이름은 CSV 파일 이름에서 `.csv` 를 뺀 것과 같아야 한다.
- 스키마에 없는 열을 CSV 에 두지 않는다. 검사가 실패한다.
- `min`·`max` 는 게임이 깨지지 않는 한계로 잡는다(체력 0 은 즉사이므로 `min: 1`). 밸런스 분석가가 권장값을 낼 때 이 범위 안에서 고른다.

## 4. 수정할 때

- balance 의 수정 요청을 받으면 반영 여부와 이유를 답하고, 바꾼 값은 명세의 「변경 기록」에 남긴다. 수치를 바꾸고 기록하지 않으면 시뮬레이션 보고서가 어느 버전을 검증했는지 알 수 없다.
- 동결 뒤에는 열 이름을 바꾸지 않는다. 코드가 열 이름으로 값을 읽는다. 열을 추가하는 것은 괜찮지만 스키마도 함께 고친다.
- 확정 폴더(`games/{slug}/data/balance`)의 파일은 직접 고치지 않는다. 작업 폴더에 새 버전을 쓰면 리더가 다시 승격한다.
